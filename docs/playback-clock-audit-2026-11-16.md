# 播放时钟检查 · 2026-11-16

基线：本地 `main` / `3a93ffc`；运行中的程序为 `1.2.0-ui-preview-ui-polish-win-x64`。本次按用户“先检查”要求进行诊断，没有修改程序、歌词、译文、偏移、播放状态或播放队列。

## 结论

时钟不是简单地每秒更新一次：正常播放使用单调计时插值，并补偿时间轴年龄和快照投递时间。但暂停/恢复路径存在可复现的秒级边界问题；连续播放的现场数据也出现约一秒的源位置跳变及直接校正。因此不能把不同步全部归因于歌词文件，也不能据此给全部歌曲统一增加固定偏移。

这些结果尚未测得相对实际歌声的绝对误差。独立探针使用同一 GSMTC 来源，不是音频真值。

- 首轮 100 个样本全部为 Paused，位置不可用；不把它记为“暂停冻结通过”。之后用户主动开始播放。

- 当前绑定的歌词文件偏移、单曲偏移及全局偏移均为 0。
- 46 条 timeline 事件读取时距其更新时间约 5–11 ms，均值约 8 ms；事件间隔均值约 1,001 ms（其中有一次相同时间戳的重复事件）。这不能证明声音输出也与这些时间戳对齐。
- 观察到相邻源位置在约 1,021 ms 内增加 2,000 ms。独立时钟相邻采样扣除自然流逝后向前校正约 934 ms。代码在误差达到 500 ms 时直接使用新目标，与此相符。没有据此断言这是用户 seek，也没有断言已确定播放器内部成因。
- 时钟比“最新一条原始整数位置”大约 200–1,209 ms，平均 681 ms。这包含正常插值推进，不能称为“歌词超前歌声 681 ms”。

## 代码与确定性复现

现有 `ClockTests` 执行 **13/13 通过**，但没有覆盖以下前两条路径。另以真实 `PlaybackClock` 和可控 `TimeProvider` 运行 8 个诊断场景，5 个满足期望、3 个不满足；这不是新增正式回归测试，也不是“全部检查通过”。

### 恢复时漏补快照投递耗时

位置：`src/LumaLyrics.Core/PlaybackClock.cs`，`Update` 的 `statusChanged && predicted.HasValue` 分支（基线第 52–55 行）。

暂停时的位置为 10 秒。5 秒后采到 Playing，但 Position/TimelineUtc 仍与暂停快照相同；再过 2 秒才投递到 UI。由于没有新时间轴证据，进入状态切换分支，把 10 秒直接锚定到处理时刻。已经播放的投递耗时被遗漏。现有“DelayedSnapshotIncludesDeliveryTimeOnlyWhilePlaying”只测首次接入，不测这条恢复分支。

### 短暂停顿可能计入推进时间

位置：同文件 `transitionStale` 与 `target` 计算（基线第 39–44 行）。

代码以“超过 2 秒”作为状态切换时旧时间轴的拦截条件，但不足 2 秒的年龄也可能全部来自暂停。例如暂停在 10.5 秒，暂停期间更新时间戳，1.8 秒后恢复并收到这份快照，当前实现把 1.8 秒当成正在播放的时间加上去。该模拟证明代码路径存在，不证明本次连续播放现场发生过相同事件序列。

以下片段可放到现有 `ClockTests` 中复现前两条问题；复用该类已有 `Snapshot` 和 `TestTime`。当前基线会失败，因此此次未把红色测试加入默认测试套件：

```csharp
[Fact]
public void ResumeDeliveryMustNotBeLost()
{
    var t = new TestTime();
    var c = new PlaybackClock(t);
    var pausedStamp = t.Utc;
    c.Update(Snapshot(t, 10000, PlayState.Paused));
    t.Advance(5000);
    var resume = Snapshot(t, 10000, timeline: pausedStamp);
    t.Advance(2000);
    c.Update(resume);
    Assert.Equal(12000d, c.PositionMs); // 基线得到 10000
}

[Fact]
public void ResumeMustNotProjectAcrossShortPause()
{
    var t = new TestTime();
    var c = new PlaybackClock(t);
    c.Update(Snapshot(t, 10000));
    t.Advance(500);
    c.Update(Snapshot(t, 10500, PlayState.Paused));
    t.Advance(100);
    var pausedStamp = t.Utc;
    t.Advance(1800);
    c.Update(Snapshot(t, 10500, timeline: pausedStamp));
    Assert.Equal(10500d, c.PositionMs); // 基线得到 12300
}
```

## 后续修复应验证的边界

1. 区分播放状态观察时刻、时间轴证据时刻和 UI 投递时刻。旧时间轴不能跨暂停外推，恢复快照在投递途中已经发生的播放时间也不应丢失。
2. 为整秒源数据设计有界的纠偏策略，但保留真实前跳/后跳/循环即时重设；不能把一切跳变都平滑掉，也不能固定加减 1 秒。
3. 在实际程序中分别测量采样、dispatcher 排队、时钟计算、UI 刷新，解释当前主窗口与探针的差值。探针直接订阅来源，不能代替 UI 线程调度测试。
4. 补充速率变化、暂停后 seek、恢复时位置尚未变化、多次快速暂停/恢复、旧事件迟到及真实换曲用例。
5. 保持原词、译文精确哈希绑定、时间戳和全部偏移不变。后续需要音频/原生进度参照，才能判断剩余误差来自播放源还是歌词时间轴。
